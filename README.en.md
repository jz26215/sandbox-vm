## Goals

The author's requirements, which are also the yardstick for "did it work":

1. Run AI tools that execute commands on their own (Claude Code, Codex CLI) on Windows, without letting them touch any other files on the computer.
2. Inside the sandbox, only **one** designated folder can be read and written.
3. Internet access only through **a proxy port the user chooses**, and only to allowlisted domains. If that proxy goes down, the sandbox goes completely offline — it must not fall back to a direct connection.
4. Apart from logging in, software in the sandbox gets no external files or data: no clipboard, SSH keys, git credentials, or GUI access.
5. Usable both from the command line and from the VS Code GUI.
6. Chinese prompts, double-click launchers on Windows.

## Architecture

```
Windows
 └─ WSL2 (Ubuntu, lightweight VM)
     ├─ sandbox-fw (iptables / ip6tables boot service, takes effect before Docker)
     └─ Docker
         ├─ box container (Claude Code / Codex / python / gcc)
         │    only data/ → /sandbox is mounted; read-only root fs; non-root; all capabilities dropped
         │    attached only to sandbox_net (internal: no route to the internet); no DNS
         │        │
         │        ▼ can only reach proxy
         └─ proxy container (tinyproxy)
              allows only HTTPS to allowlisted domains on the given ports (default 443)
                  │ egress NIC sbx-egress
                  ▼ sandbox-fw: may only connect to this one IP:port
              proxy software on Windows (upstream proxy) ──► internet
```

In one sentence: **box has no route, proxy only honors the allowlist, and the host firewall lets proxy go to exactly one place.**

| Layer | What it does | What it defends against |
|---|---|---|
| 1. box container | internal network only, no DNS, only `data/` mounted, read-only root, non-root, `cap_drop: ALL` | programs ignoring proxy settings and connecting directly; DNS tunneling; reading/writing other files; modifying the system |
| 2. proxy container | tinyproxy default-deny, only allowlisted domains and given ports | reaching sites outside the allowlist; connecting by raw IP |
| 3. sandbox-fw | proxy's egress NIC may only reach the upstream proxy IP:port; all IPv6 rejected; cannot initiate connections to the WSL host | direct internet access if proxy is bypassed or misconfigured; falling back to direct connection when the upstream proxy is down |

Design rationale: [docs/设计思路.md](docs/设计思路.md) (Chinese). Pitfalls encountered: [docs/排查记录.md](docs/排查记录.md) (Chinese).

## What works out of the box, and what needs configuration

Legend: ✅ tested by the author ⚙️ must be configured for your environment 🧪 written but not thoroughly verified ⚠️ known limitation

### ✅ Tested by the author

| Part | Test result |
|---|---|
| box / proxy two-container isolation | Self-test all passed: Windows drives not visible, read-only root, non-root, no external DNS, no route when bypassing the proxy |
| Allowlist + port restriction | Non-allowlisted domains rejected, raw-IP connections rejected, allowlisted domains work |
| Egress via upstream proxy | `UPSTREAM_PROXY=auto:<port>` finds the Windows host IP automatically |
| Host firewall sandbox-fw | Direct connections from proxy to an IPv4 address, a domain, and IPv6 are all rejected; only the upstream proxy IP:port is reachable |
| Offline test | After quitting the proxy software on Windows, all HTTPS and HTTP from the sandbox fails; it recovers automatically when the proxy is back. Tested both by really quitting and by simulation |
| Claude Code + Codex CLI in the sandbox | Both install and launch; tools are baked into the image, login data lives in `data/` and survives image rebuilds |
| VS Code into the sandbox | Dev Containers attaches to the container; Claude / Codex extensions installed on the container side |
| VS Code channel hardening | No SSH / GPG / git credential forwarding; programs in the terminal cannot make Windows open web pages; X11 GUI channel blocked with a read-only empty directory. Each item checked, see [docs/VSCode.md](docs/VSCode.md) (Chinese) |
| Resource limits | CPU and memory limits configurable in `.env`; tested at 4 cores / 4 GB |
| Time zone | Container time zone can be changed |

### ⚙️ Needs your own configuration

| Item | How |
|---|---|
| Upstream proxy | Set `UPSTREAM_PROXY=auto:<your proxy port>` in `.env`; the proxy software must have "Allow LAN connections" turned on |
| Allowlist | Edit `allowlist.txt` for the tools you use. Defaults: GitHub, PyPI, npm, Anthropic, OpenAI, VS Code server |
| Docker pulls through proxy | If Docker Hub is unreachable directly, run `setup/4-设置Docker代理.sh <port>` |
| Linux user | The sandbox uses uid 1000. The first WSL user is usually 1000; if not, `data/` will not be writable |
| WSL distro name | Scripts assume `Ubuntu` |
| Windows launchers | `windows/打开沙箱文件夹.bat` needs your Linux user name |
| VS Code user settings | Run `tools/vscode_settings.py`; it lists the changes, only applies them after you type `y`, and backs up the original file |
| Other | Time zone, resource limits, and operation log path are all in `.env` |

### 🧪 Written but not thoroughly verified

- **Port restriction for plain HTTP**: tinyproxy's `ConnectPort` only governs HTTPS (CONNECT). Whether plain HTTP to other ports on allowlisted domains gets through was not tested.
- **Firewall rules after a reboot**: per Docker's docs, rules in the `DOCKER-USER` chain are preserved. It has kept working in the author's environment, but no dedicated reboot test was done.
- **`setup/3-可选-加固WSL.sh`**: hides Windows drives from the whole WSL and disables calling Windows programs. Not run by the author.
- **`dev.containers.forwardWSLServices`**: not sure this VS Code setting name is correct. Harmless if wrong.
- **Login callback port**: with VS Code port auto-forwarding off (`remote.autoForwardPorts=false`), whether the callback port used for extension login (e.g. 1455) still gets forwarded was not verified.
- **Claude Code login flow inside the sandbox**: not confirmed step by step by the author.
- **Windows Home edition**: WSL2 should support it; the author has not confirmed their own edition.

### ⚠️ Known limitations (not possible yet, or unsolved)

- **VS Code connection often hangs for about 4 minutes**: it is stuck on a 240-second timeout inside the Dev Containers extension; root cause not found. Once it connected quickly right after WSL had been restarted. Details in [docs/排查记录.md](docs/排查记录.md) (Chinese).
- **VS Code extension channels cannot be closed**: extensions (including the official Claude and Codex ones) can read the Windows clipboard; can make the Windows browser open a URL — and the URL can carry data, outside the allowlist; and can request the accounts you are signed into in VS Code (requires your consent). None of these exist when using only the command line (`./sb.sh claude`, `windows/打开Claude.bat`).
- **Allowlisted domains can themselves be used to exfiltrate data**, e.g. pushing code to github.com. A domain allowlist cannot stop this; for sensitive projects, trim the allowlist to the minimum.
- **No TLS inspection**: tinyproxy only looks at the host name in the CONNECT request. Wildcard domains (e.g. `*.githubusercontent.com`) allow a fairly broad range.
- **Not a separate VM**: containers share one Linux kernel with WSL. A container escape would reach WSL, and WSL can see Windows drives by default (`setup/3` can turn that off).
- **The proxy container can still resolve DNS** via Docker's built-in DNS; the box container cannot.
- **System information is visible**: CPU model, kernel version and similar can be seen from inside the sandbox.

## Non-goals

- **No fingerprint, region, or device spoofing of any kind**, and not for evading any service's terms or risk controls. The time-zone feature exists only for testing time-related code.
- Please follow the terms of use of the services you use (Anthropic, OpenAI, etc.).

## Quick start

1. **Install WSL**: run `setup\1-安装WSL.ps1` in an administrator PowerShell, reboot, open Ubuntu and set a user name and password.
2. **Prepare config**: download this repo to Windows, e.g. `D:\sandbox-vm`. Copy `.env.example` to `.env` and fill in `UPSTREAM_PROXY`.
3. **Install Docker**: in Ubuntu run `bash /mnt/d/sandbox-vm/setup/2-安装Docker.sh /mnt/d/sandbox-vm`; it copies the project to `~/sandbox-vm`. Then run `wsl --shutdown` in PowerShell and reopen Ubuntu.
4. **Pull images through the proxy** (if Docker Hub is unreachable directly): turn on "Allow LAN connections" in your proxy software, then run `bash ~/sandbox-vm/setup/4-设置Docker代理.sh <port>`.
5. **Start**: `cd ~/sandbox-vm && ./sb.sh up && ./sb.sh test`. The last 3 checks (proxy direct connection) only pass after the network hardening is installed.
6. **Network hardening**: `bash tools/install-fw.sh` (asks for your Linux password).
7. **Offline test** (optional): `bash tools/nettest.sh`.
8. **Daily use**: `./sb.sh claude`, `./sb.sh codex`, `./sb.sh shell`; or double-click the .bat files in `windows\` on Windows.
9. **VS Code**: see [docs/VSCode.md](docs/VSCode.md) (Chinese).

Running `./sb.sh` with no arguments lists all commands: change time zone, add/remove allowlist entries, change ports, change upstream proxy, and so on. Script messages are in Chinese.

## Related projects

After building this, the author found there are already quite a few similar approaches. The author has **not tried these one by one**; descriptions come from each project's own page, for comparison:

- [Claude Code devcontainer firewall script (gist)](https://gist.github.com/mmizutani/01d47aa43f0593bfd1c754d0898f7d5c): based on the `init-firewall.sh` from Claude Code's official devcontainer, iptables allowlist only
- [MyKEms/claude-code-sandbox](https://github.com/MyKEms/claude-code-sandbox): Dev Container template with an allowlist-only proxy and persistent login
- [FoamoftheSea/claude-code-sandbox](https://github.com/FoamoftheSea/claude-code-sandbox): also internal network + proxy, using Squid to read the TLS SNI for the allowlist
- [foxirain/agent-egress-lock](https://github.com/foxirain/agent-egress-lock): Docker + Squid + host firewall to constrain AI-agent egress
- [EraPartner/Lockbox](https://github.com/EraPartner/Lockbox): devcontainer egress lockdown, firewall + Squid allowlist
- [thiagolmoraes/leash](https://github.com/thiagolmoraes/leash): with TLS inspection, domain allowlist and syscall monitoring
- [agent37-platform/claude-code-docker](https://github.com/agent37-platform/claude-code-docker), [itscooleric/clide](https://github.com/itscooleric/clide): Claude Code and similar tools in containers with an egress firewall

What this project focuses on (which does not mean others lack it): the Windows + WSL2 scenario; chaining egress to the user's local proxy-software port, with "proxy down means offline" enforced at the host-firewall level; listing each channel that opens when VS Code connects into the sandbox; Chinese docs and double-click launchers.
